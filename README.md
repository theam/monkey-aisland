# The Monkey AIsland

A point-and-click adventure game where you try to become the greatest engineer of all
time. It is definitely not inspired by any classic game you may have played when you
should have been doing your homework. It is, however, a recruiting funnel for
[The Agile Monkeys](https://theagilemonkeys.com).

Three scenes: a lookout point above the harbour, a dock with a small and unwanted art
exhibition about the company, and a bar called El Patilla containing three engineers,
a barman, and two monkeys who decide who gets hired.

```bash
npm install
npm run dev        # http://localhost:5173
npm run lint       # static code checks
npm test           # unit tests
npm run test:game  # browser-level game checks and screenshots
npm run build      # -> dist/, a static site
npm run preview    # serve the built site
npm run shots      # screenshots + checks (needs `npm run dev` running)
npm run social-card # re-render the link preview image (needs `npm run dev` running)
npm run promo-video # render the promo video to video/ (needs `npm run dev` and ffmpeg)
```

`npm run shots` drives the real game in headless Chromium: it writes every screen
to `shots/` at an exact integer scale (`-- --scale 4`), walks every conversation
looking for dead ends and nodes with no way out, and runs pixel assertions for
the specific bugs that have bitten this project — a line drawn through one of
the dock paintings, lettering overflowing its sign, dialogue timing that clamps
long lines into being unreadable. It exits non-zero when something regresses, so
it works in CI. Judging 320×200 pixel art needs full-resolution images, not
eyeballing a scaled-down browser window.

The link preview (the picture LinkedIn, Slack, WhatsApp and X show when someone
shares the game) is `public/social-card.png`: the title card at 4x, cropped to
1200×630. `npm run social-card` photographs it from the running game, so rerun
that whenever the title card changes. The tags are in `index.html`, and
`npm run shots` checks that the image they point at exists at the size they claim.

### The promo video

Not a trailer: a trailer for a five-minute game would last about as long as the
game. Instead the trailer is a character — a used-ship salesman in a loud jacket,
arms going, selling the company and the game at speed on a black stage — until
the player asks whether it wouldn't be faster to just play it.

The script is `src/promo/script.ts`, written like a screenplay: lines, pauses,
the salesman's body language, and the cues (the door, the music stopping). Edit
it and open <http://localhost:5173/promo.html> to watch it with the music; it
plays, scrubs, and switches between 16:9 and 1:1. Every claim it makes about the
company is true — keep it that way.

```bash
npm run promo-video                      # video/monkey-aisland-promo-wide.mp4, 1920x1080
npm run promo-video -- --format square   # 1080x1080, for feeds
npm run promo-video -- --no-crickets     # leave the awkward silence silent
```

Every frame is painted by the game's own code (the salesman is a puppet like the
rest of the cast, `src/promo/salesman.ts`), piped raw to ffmpeg and scaled up
with nearest-neighbour by a whole number, so the pixels stay square. The theme
fades in from where the tune drops, stops dead at the interruption, and fades
back in from the same bar when the salesman recovers. `promo.html` is a dev page:
`vite build` only builds `index.html`, so the promo never ships with the game.

## What is in here

| | |
|---|---|
| **Rendering** | 320×200 indexed-colour framebuffer, integer-scaled to the window. Every pixel of art is generated by TypeScript at load time. |
| **Art** | No image files. Backgrounds are painted procedurally into an offscreen buffer; characters are built from a shared "puppet" renderer plus hand-drawn ASCII overlays. |
| **Music** | The provided main theme (`public/audio/`), intro-once then looping. A complete synthesised alternative is one config word away — see [Music](#music). |
| **Sound effects** | No audio files: every effect is synthesised in WebAudio at runtime. |
| **Text** | A hand-authored 5×9 bitmap font with Spanish glyphs, because people's names have accents in them. |
| **Content** | Every word lives in YAML under `public/content/`, loaded at runtime. |
| **Progress** | Not saved. The game is a few minutes long, so every visit starts at the top of the path and the intro is always seen. |
| **Size** | ~250 KB of code (~50 KB gzipped) plus a 2.9 MB music file. No runtime dependencies except `js-yaml`. |

Apart from that one music file, there is not a single binary asset in this repository —
all the art is code. That is partly a technical flex and partly the point: the game is
text, and text can be reviewed in a pull request.

## Editing the game without being a programmer

Everything the game says is in `public/content/`. Edit a `.yaml`, reload the page, done
— no build step, no TypeScript, nobody needs to install anything.

```
public/content/
  game.yaml              config: the hiring chat URL, which files to load, audio defaults
  en/
    ui.yaml              verbs, the title card, dialogue pacing, the sarcastic
                         fallback lines, interstitials, the hiring-chat copy
    scene-lookout.yaml   the lookout: hotspots, exits, where Nayara stands
    scene-dock.yaml      the dock: the six boards, the ship, the barrels
    scene-bar.yaml       El Patilla: the cast and the furniture
    dialog-nayara.yaml   the lookout's conversation
    dialog-bar.yaml      Giorgio, Big-John, Chaxi (including the name gag), the barman
    dialog-monkeys.yaml  Jaime and Javi, and the two challenges
    dialog-duel.yaml     the code review duel
```

### Adding a line of dialogue

```yaml
nayara:
  speaker: nayara          # who speaks lines that don't name a speaker
  start: root
  nodes:
    hub:
      choices:
        - text: 'What does it pay?'      # what the player says
          goto: money                    # which node to go to
          once: true                     # hide this option after it is used
    money:
      lines:
        - 'Straight to it. Good.'                      # spoken by `speaker`
        - { who: bigjohn, text: 'He asked in a bar.' }  # or name someone else
      set: [asked_about_money]            # remember it happened
      goto: hub
```

Other things a node can do:

| key | meaning |
|---|---|
| `if: [flag]` / `unless: [flag]` | on a choice: only show it when flags match |
| `branch: [{if: [...], goto: x}, {goto: y}]` | conditional continuation, first match wins |
| `action: { type: chat }` | show the last screen, with the link to the hiring chat |
| `action: { type: interstitial, id: to_the_chat }` | the same last screen |
| `action: { type: interstitial, id: credits }` | a black screen with a Continue |
| `action: { type: dialog, id: duel }` | hand off to another conversation |
| `action: { type: scene, to: dock, entry: west }` | move the player to another scene |
| `emote: laugh` | on a line: use the speaker's `laugh` frame while they say it |

Content is validated at load: a typo in a `goto` produces a readable error on the boot
screen naming the file, the node and the problem, instead of a blank canvas.

You never have to write an exit for a conversation. One is added to the bottom row of
every page of options automatically, labelled from `ui.yaml → labels.leave`. If you *do*
write your own (`exit: true`), the automatic one steps aside.

### The opening

Two screens, both in `ui.yaml`:

- `start` — the TAM mark, the wordmark, and the "press start" prompt. Only text here; the
  mark itself is drawn in `src/art/scenes/start.ts`.
- `title` — the stacked title lines (each with a pixel `scale`), and a `roll` of captions
  with the second each appears at. `ends_at` is when it hands over to the game; keep it
  equal to the music's `intro_end` so the game starts as the theme drops.

Note that the lookout deliberately has **no** `on_enter` narration: the intro has just
said all of it, and being talked at twice before touching anything is not an opening.
Put it back if you ever drop the intro.

### Adding a thing to look at

```yaml
hotspots:
  - id: barrels
    name: the barrels          # appears in the sentence line: "Look at the barrels"
    rect: [612, 104, 40, 24]   # x, y, width, height in room pixels
    walk_to: [606, 134]        # optional: walk here first
    verbs:
      look: 'Barrels of Arehucas.'
      open:
        say: 'Sealed.'
        sfx: mug
      pickup: 'Full barrels weigh more than my career prospects.'
```

Any verb you do not write gets one of the rotating sarcastic fallbacks from
`ui.yaml → defaults`. Add `?debug` to the URL to see walkboxes and hotspot rectangles
drawn over the scene while you place them.

## Music

The soundtrack is chosen with one word in `public/content/game.yaml`:

```yaml
audio:
  source: file     # the provided main theme in public/audio/
  # source: synth  # the original scores written for this game, no audio files
```

**`file`** plays `public/audio/main-theme.mp3`. The track has a ~10-second
intro before the main theme, and a closing passage at the end, so it is not simply
looped. It plays once from the beginning, and thereafter loops only the musical section:

```yaml
files:
  theme:
    src: audio/main-theme.mp3
    intro_end: 10.031  # the intro plays once; the loop begins here
    loop_end: 175.032  # jump back before the closing passage and fade-out
    crossfade: 0.35    # overlap at the join, so a near-enough loop point sounds fine
```

Every scene maps to the same track (`scene_tracks.default`), which is what keeps the
music running across scene changes rather than restarting — walking into the bar must not
replay the intro.

**Tuning the loop.** The endpoints are aligned to the track's 95.7 BPM pulse: the intro
hands over after four bars, and the loop closes 264 beats later before the ending.
Rather than waiting nearly three minutes to hear each attempt:

```bash
open "http://localhost:5173/?loopcheck"
```

That jumps straight to a few seconds before the join. `window.__loopCheck()` in the
console does the same thing on demand. Edit the numbers, reload, listen again.

**`synth`** switches to the three original compositions (`src/audio/scores.ts`) —
calypso-inflected, one per scene, written for this game and owned by us.

## Wiring up the hiring chat

The game hands candidates off to TAM's hiring chatbot in a new tab. It does not collect
or transmit candidate details itself, and the Cloudflare Worker exposes no application
API. `public/content/game.yaml` contains the public destination:

```yaml
chat:
  url: https://hiring.theagilemonkeys.com/?utm_source=monkey-aisland
```

The `utm_source` value is the chat's own arrival tag. The chat reads it silently from
the URL, stores it against the conversation, and groups it in the channel funnel of its
admin panel — so "how many people the game actually sent" is answered there, next to
every other channel. The tag must be lower case with hyphens; anything else is flagged
as malformed and shown apart.

When the player arrived from an ad, the game adds that link's `utm_medium`,
`utm_campaign`, `utm_content` and `utm_term` to the chat link, so the chat can tell which
campaign a candidate came from (it stores medium, campaign and content; `utm_term` it
ignores for now). `utm_source` stays `monkey-aisland`: the ad's own source is in the
game's analytics, not in the chat. Only those tags are passed, normalised as the chat
normalises them, never a click id such as `twclid` — see
[campaign.ts](src/engine/campaign.ts).

Do not add names, email addresses, access tokens, or other personal or sensitive values
to this URL. The chat guides the candidate through the first conversation, stores the
answers, and feeds the completed conversation to the hiring team for review.

The last screen links straight to the chat, with a way back to the island. It tells
players they do not have to do it in one go: the chat keeps the conversation in their
browser and picks it up when they return. The game shows no privacy notice of its own
for the chat, because the game collects nothing there. The chat carries its own notice,
at the point where it collects anything: what is kept and why, a link to TAM's privacy
policy, and a way to delete the conversation. The game's Privacy panel covers only what
the game itself counts.

## Knowing whether any of this works

The game counts how far people get. It never talks to PostHog itself: each event is
posted to `/api/event` on the game's own host, where a small Cloudflare Worker
([`worker/`](worker/)) checks it and passes it on. The PostHog project tokens live only in
the Worker's secrets — not in this repository, not in the page — so nobody can lift one
from the browser and fill the funnel with whatever they like.

```yaml
analytics:
  provider: posthog   # or: none
```

The Worker is strict about what it forwards:

- **Only what the game says.** Every event name and property is on an allowlist in
  [`worker/events.ts`](worker/events.ts), with its type and shape. Anything else is
  dropped whole.
- **Only from the game's own pages.** The request's `Origin` has to be the host the
  Worker is serving.
- **At a human pace.** At most 60 events a minute from one address, through Cloudflare's
  rate-limiting binding (`wrangler.jsonc`).
- **On its own clock.** Timestamps are the Worker's, not whatever a client claims.

None of that makes a fake event impossible — anything a real browser can send, a script
can send too — but it limits a forger to saying what the game says, at a rate a person
could, through an endpoint we can tighten or switch off.

Which project an event lands in depends on where the game is running. The hosts in
`PRODUCTION_HOSTS` (`wrangler.jsonc`) go to the production project; everything else — a
Worker preview URL, `wrangler dev` — goes to the development project, or nowhere if it
has no token. The tokens are Worker secrets:

```bash
npx wrangler secret put POSTHOG_KEY       # production project token (phc_…)
npx wrangler secret put POSTHOG_DEV_KEY   # optional: preview URLs and wrangler dev
```

Without a token the Worker accepts events and drops them. `npm run dev` has no Worker at
all, so nothing leaves a local run, and automated browsers (the CI checks) never send.
Add `?analytics` to the URL to print events to the console instead of sending them. That
is the fastest way to see the funnel while editing content.

### What it records

Every event fires **at most once per visit**, so each one is a funnel step and the
funnel can be read in any tool that builds funnels from event names:

```
game_opened → game_started → reached_lookout → reached_dock → reached_bar
            → won_duel → handoff_shown → chat_opened
```

Two more sit beside the funnel: `intro_ended` (`skipped`, `seconds`), which shows
whether the title card earns its ten seconds, and `dialog_opened` (`dialog`), which
shows which conversations people bother with at all. `game_opened` carries `touch` and
`portrait`, because the game has a separate touch layout. Every event carries `at`,
whole seconds since the page opened, which is how you see where the middle drags.
`chat_opened ÷ game_opened` is the number the game exists to move.

Every event also carries the `utm_` tags of the link the visit arrived by, so a funnel
can be broken down by ad, audience or language. PostHog adds the country: the Worker
passes on the address the request came from, PostHog looks up the country, and the
project's settings discard the address and anything finer than the country. The tags go
on every event rather than once, because without person profiles there is nowhere else
for them to live.

`reached_*` comes from the first visit to each scene, so a fourth room joins the funnel
with no analytics code to touch. `won_duel` is the one content flag that counts as
progress, allowlisted in `attachAnalytics` in [game.ts](src/engine/game.ts). Nothing
about the island is reported until PRESS START: the lookout is painted behind the title
card, so reporting it on load would count everyone who opened the page as having reached
the island.

What it deliberately does **not** record: what anyone answers in a conversation (the
duel's options are attitudes, and recording them would measure candidates rather than
the game), walking back and forth between rooms, anything that survives the tab, the IP,
any location finer than the country, and ad networks' click ids.

If you add an event, add it in the same change to the Worker's allowlist
(`worker/events.ts`) and to the first paragraph of the Privacy panel (`counting` in
`ui.yaml`), which tells players what is counted. Without the first it never arrives;
without the second the panel is wrong.

### Where the other half of the funnel lives

The game's funnel stops at `chat_opened`. What happens next belongs to the hiring chat,
which runs its own: the `?utm_source=monkey-aisland` tag on the chat link files every
arrival under that name in the chat's **Canales** panel, broken down by entered, wrote,
gave an email, finished phase 1, returned, completed. Join the two at the boundary —
`chat_opened` here, `entered` there — rather than trying to follow one person across it.

## Playing it

- **Start screen → intro → game.** The start screen carries the TAM mark and waits for a
  press; that press is the gesture browsers demand before audio may play, so the music is
  already running when the title card appears. The intro then plays itself in step with
  the theme and hands over exactly as the tune drops. A press skips it; `?skipintro`
  skips both screens.
- Click the floor to walk. Click a verb, then a thing.
- The sentence line at the bottom always says what is about to happen.
- **The verb resets to "Walk to" once a command runs**, like the original — so you can
  never get stuck holding a verb and unable to walk. `Esc` or right-click also clears it.
- **Right-click does the obvious thing:** *Talk to* a person, *Look at* anything else.
- **Dialogue plays itself.** Lines clear on a timer, so a conversation runs start to
  finish without a single click; clicking just skips ahead. Pacing is in `ui.yaml`.
- **Every set of dialogue options has a way out** on the bottom row, on every page, whether
  or not the writer remembered to add one.
- Keyboard: verb shortcuts (`o c s g p y u l t`), `1`–`6` pick dialogue options,
  `Tab` cycles through things in the room, `Enter` interacts, `Space`/`Esc` skips a
  line, `m` mutes.
- `?debug` draws the walkbox and hotspots. `?loopcheck` jumps to the music loop join.

Nothing is saved. Every reload is a fresh game, which is deliberate: the run is only a
few minutes long and the intro is part of the joke. The only things that persist are
whether you muted the sound and, if you asked, that you don't want your visits counted.

## The two challenges

The monkeys announce two trials and then send the player to the hiring chat. The trials are
designed, not implemented — deliberately, because the point of the prototype is the
funnel. When you do build them:

1. **The Loose Plank** — a small repository and a true story about it misbehaving in
   production. Find the cause, fix it, write ten lines on why. Ninety minutes, not a
   weekend. AI assistance explicitly allowed, because the thing being measured is
   whether you can tell when the confident answer is wrong.
2. **The Second Opinion** — a code review duel. Review a pull request that was broken
   on purpose in an interesting way, then defend the review for thirty minutes against
   someone pushing back. Nobody fails for being wrong; people fail for defending a
   position they stopped believing in four comments ago.

A playable prototype of the second one is already in the game: talk to Giorgio and offer
to review some code with him, outside. It lives entirely in `dialog-duel.yaml`, so
adding rounds is a copy-paste job.

## Deploying

The build is a folder of static files with relative paths, so it works from any host and
any subdirectory; only the analytics endpoint needs the Worker. The live site runs on
Cloudflare Workers Static Assets, deployed by [the CI workflow](.github/workflows/deploy.yml):

| Trigger | What runs |
|---|---|
| Pull request | lint, typecheck, unit tests, build, a Worker dry run and the browser game checks. No deploy. |
| Push to `main` | the same checks, then a deploy to production |
| Manual run | a deploy of any branch, tag or commit SHA, for rolling back |

The deploy job runs in the GitHub `production` environment, which only `main` may deploy
from. It needs the secret `CLOUDFLARE_API_TOKEN` there (Cloudflare's *Edit Cloudflare
Workers* template, scoped to the one account) and the variable `CLOUDFLARE_ACCOUNT_ID`,
which is an identifier rather than a credential. Pull requests never see either. The
custom domain is attached in the Cloudflare dashboard, not in `wrangler.jsonc`, so a
deploy never touches it.

## Code layout

```
src/
  engine/        framebuffer, palette, font, drawing, input, actors, dialogue runner,
                 verb interface, YAML loader, save state, the DOM overlay,
                 analytics.ts (cookieless, off unless game.yaml turns it on)
  art/
    puppet.ts    the character renderer everyone is built from
    cast.ts      the eight characters, as specs plus ASCII overlays
    props-*.ts   reusable scenery: sky, sea, cliffs, palms
    scenes/      one painter per room
  audio/         synth voices, the three scores, sound effects, the scheduler
worker/          the Cloudflare Worker behind /api/event: checks analytics events
                 and forwards them to PostHog
```

Two things worth knowing if you touch the engine:

- **All art is deterministic.** Painters take a seeded RNG; nothing calls
  `Math.random()`, so the island looks identical on every load, forever.
- **Time comes from `engine/clock.ts`**, not `performance.now()`. That keeps the game
  frame-rate independent and lets a hidden tab or a test step it deterministically via
  `window.__step(ms, steps)`. That hook, `window.__game` and `window.__loopCheck` only
  exist on the dev server (`npm run dev`), which is what the browser checks run against.
- **Analytics can never break the game.** Every path in `engine/analytics.ts` swallows
  its own errors, and the whole module is a no-op until it is configured. If you add an
  event, add it where the thing actually happens, and send identifiers — not prose.
